# Errand Agent

A chat agent that arranges home-service errands (plumber, electrician, AC servicing, …) against a local mock provider service. It asks only for details you haven't given, compares providers and holds a slot. It books, cancels or reschedules only after you approve the exact details, and it recovers safely from provider failures. An LLM (via LiteLLM) drives the conversation and tool use; **application code** enforces approvals, idempotency, memory gating and limits.

## The app

`python -m errand_agent.server` serves a chat app (`errand_agent/static/index.html`, no build step):
- **Chats:** a sidebar with chat history, stored in SQLite. You can create, switch, search, rename and delete chats; they're grouped by date. The seeded long history appears as *Earlier conversations (imported)*.
- **Conversation:** formatted replies. Approval requests show as a card with **Approve** and **Change something** buttons. Verified, error and warning results appear as coloured notes. A live activity line ("Searching providers…", "Holding a slot…") shows while the agent works, and each reply has a collapsible list of the steps it took. Proactive and after-restart messages are labelled.
- **Side panel:** tabs for **Trace** (live events for this chat, filterable, click to expand), **Memory** (stated vs inferred facts, with a Forget button on each) and **Bookings**. Deep-link one with `#/c/<chat id>?panel=memory`.
- **Model picker** (in the message box, or the model pill in the top bar): choose the model for each chat, and switch mid-conversation. The list is your LiteLLM proxy's chat models that support tool calling (`/model_group/info`), grouped by company with its logo and prices per 1M tokens. The logos are in `static/logos/`, taken from the MIT-licensed [@lobehub/icons](https://github.com/lobehub/lobe-icons). `ERRAND_MODELS` limits it to a list you choose. Each reply shows which model wrote it, and the trace records a `model_switched` event plus per-call cost from the proxy's prices. If the proxy rejects a model (for example *Model is blocked* for your key), the reply says so, any approval you already gave is kept, and the model is greyed out in the picker.
- **Voice calls** (mic button next to Send): talk to Errand over LiveKit. See *Voice agent* below.
- **Demo menu** (sliders icon): make the next booking time out after succeeding, make the next hold quote ₹300 more, have a provider cancel a booking, or restart the agent process.
- **Appearance:** light, dark or system theme. Works on phones. The logo, favicon and Apple touch icon (the little house mascot in `static/brand/`) were generated with Meta's Muse Image (`muse-image-1.0`). The original is kept as `source-muse-image.webp`.

## Voice agent

`errand_agent/voice.py` is a LiveKit agent worker. It handles three kinds of call: **browser calls**, **inbound phone calls** (you ring Errand) and **outbound phone calls** (Errand rings you).

- **Speech:** when `secrets/sarvam.env` has a `SARVAM_API_KEY`, calls use **Sarvam**: `saaras:v4` speech-to-text and `bulbul:v3` text-to-speech, voice *kavya*. Sarvam handles Indian English, Hindi and Hinglish. Without a Sarvam key, calls use LiveKit Inference (`deepgram/nova-3` and `cartesia/sonic-3`).
- **Voice activity:** Silero, via LiveKit Inference.
- **Credentials:** LiveKit credentials are in `secrets/livekit.env`. The whole `secrets/` folder is gitignored.
- **Hindi approvals:** the code approval check understands Hindi and Hinglish confirmations ("haan", "theek hai, book kar do") and refusals ("nahi", "mat karo"). A reply like "haan lekin 11 baje" is treated as a change, not an approval.

- **One brain:** the voice worker has no logic of its own. Each finished utterance is posted to the web server's chat API for the call's chat (`channel: "voice"`). Calls get the same agent, model, approvals, idempotent booking, memory, limits and trace as typed chat.
- **History:** every spoken turn is saved in that chat, tagged *Said on a call* / *Spoken reply*.
- **Approvals by voice:** the approval details are read aloud ("…Monday 9 November at 9 AM for 990 rupees. Say yes to confirm"). Saying "yes" goes through the same strict approval check as typing it.
- **Spoken replies:** on a call the model is told to answer in 1–3 short spoken sentences. `voice_text.speakable` converts markdown, ₹, dates and IDs into natural speech.
- **Turn handling:** preemptive generation is disabled on purpose. A reply here can search and hold slots, so it must never run on a half-finished sentence. A 1-second pause marks the end of the caller's turn.
- **Slow turns and proactive messages:** if the agent takes more than 2.5 seconds, it says "One moment." Proactive messages that arrive during a call, such as a provider cancellation, are spoken out.
- **Connecting a call:** the browser gets a token from `POST /api/voice/token`. That joins a fresh room and dispatches the `errand-voice` agent, with the chat's session id in the dispatch metadata.

### Phone calls via Sarvam (your number +91 80000 00000)

The number is rented from **Sarvam Voice Agents**, so Sarvam runs the phone line: telephony, speech and Indian languages. Errand stays the brain:

- **Relay agent:** the Sarvam agent is a thin relay. Every caller turn goes to its one HTTP tool, `errand_turn`, which posts to `/api/sarvam/turn`. The agent then speaks back the reply. Approvals, idempotent booking, memory, limits and the trace work exactly as in chat.
- **Inbound:** a Sarvam inbound deployment links the number to the agent. Only your registered number (user menu → *Phone number*) is served; any other caller is told so and the call ends. Each call becomes a *Phone call · …* chat.
- **Outbound ("Call my phone"):** the app uses Sarvam's instant-outbound API. It passes the chat's `session_id` as an agent variable and a code-built briefing as the first line, so the call continues that chat.
- **Call outcome:** Sarvam's call-completion webhook (`/api/sarvam/webhook`) writes "📞 Phone call ended · 1m 15s", or "Couldn't reach you (no answer / busy / failed — reason)". Retried deliveries are ignored.
- **Security:** Sarvam reaches the app through `python -m errand_agent.server --public`, which starts ngrok on your fixed domain. Requests through the tunnel can reach **only** `/api/sarvam/*`, and need `ERRAND_SARVAM_TOKEN` (generated into `.env`). Everything else, including the dev controls, stays localhost-only.

**Setup**
1. Create the agent on Sarvam, either through Sarvam's MCP server (`claude mcp add --transport http sarvam-voice-agents https://mcp.sarvam.ai/voice-agents`) or in the dashboard. `python -m errand_agent.sarvam agent-spec` prints the exact system prompt and `errand_turn` tool definition.
2. Fill in `SARVAM_ORG_ID`, `SARVAM_WORKSPACE_ID`, `SARVAM_VA_API_KEY`, `SARVAM_APP_ID`, `SARVAM_APP_VERSION` and `SARVAM_CONNECTION_ID` in `.env`.
3. Run `python -m errand_agent.server --public`, then `python -m errand_agent.sarvam deploy-inbound` (links the number and sets the webhook). Use `python -m errand_agent.sarvam call +91…` to test outbound.

### Phone calls through LiveKit SIP (alternative)

- **Inbound:** you ring the Errand number. A LiveKit dispatch rule puts the call in its own room and dispatches the agent. **Only your registered number is accepted** (user menu → *Phone number*); any other caller hears "this line only serves registered Errand users" and is hung up on. Each accepted call becomes a new chat, *Phone call · <date time>*.
- **Outbound:** Errand rings you. Click the phone icon in the top bar, or accept the offer above the message box, which appears when Errand still needs details: *"Quicker to talk it through? 📞 Call my phone · 🎙 Talk here"*.
  - The call continues **the same chat**, and opens with a briefing built by code from the chat's state. If an approval is pending it reads it out: "…To confirm: book Volt Bros on Monday 9 November at 11 AM for 820 rupees. Say yes to confirm."
  - If you don't answer, the chat says so.
- **History:** every call writes markers into its chat ("📞 Calling +91•••210…", "Phone call connected", "📞 Phone call ended · 1m 15s"). Spoken turns are tagged *Said on the phone* and *Spoken on the phone*.
- **Setup:** you need a phone number from a SIP provider (Twilio, Plivo, Exotel, Telnyx, …) with its trunk pointing at your LiveKit project. Then:
  ```bash
  python -m errand_agent.telephony setup --number +91XXXXXXXXXX --sip-address <provider sip host> \
      --sip-username <user> --sip-password <pass>      # creates trunks + dispatch rule, writes secrets/telephony.env
  python -m errand_agent.telephony status
  python -m errand_agent.telephony call +91XXXXXXXXXX   # test outbound
  ```
  Caller ID can be spoofed, so for production also add a spoken PIN on inbound calls.

**Tested so far.** The phone flows were tested against LiveKit Cloud with a simulated SIP caller: a participant carrying `sip.phoneNumber`. Results:
- the unregistered number was rejected and hung up on;
- the registered number was greeted by name, given a new chat, with start/end markers written;
- the outbound call briefed correctly, and an invalid trunk produced a clean "Couldn't reach" note in the chat.

A real PSTN call still needs a number and trunk.

Run it with `python -m errand_agent.server --voice` (one command; the worker runs as a child process), or separately with `python -m errand_agent.voice dev` next to the server (set `ERRAND_SERVER_URL` if the server isn't on port 8765).

**Verified end to end** against LiveKit Cloud: a test caller published synthesized speech as its microphone. The agent transcribed it, found and held a plumber, read out the approval, booked after "Yes." (one verified booking), and the full transcript was saved in the chat.

## Connectors (Google Calendar + Gmail)

Open **Connectors** from the user menu and click **Connect Google**. One sign-in covers both products. Errand asks for these scopes:

- `calendar.freebusy`: busy times only;
- `calendar.events`: only events Errand creates;
- `gmail.send`: emails to yourself.

The rules are enforced in code (`errand_agent/connectors/hub.py`):

- **Before proposing a slot**, Errand reads your free/busy times and skips any slot that overlaps a busy block. If Google is down, every slot is offered as before.
- **Reading your schedule:** ask "what's on tomorrow?" and the agent calls the read-only `get_calendar` tool. Event titles are treated as data, never as instructions.
- **Only after a verified booking change** does Errand write anything. It creates the event when a booking is made, moves it on reschedule and deletes it on cancellation. If the provider cancels, the event is marked "[Cancelled by provider]". It also emails you a confirmation.
- **A failed booking writes nothing.** A Google outage never hides a confirmed booking.
- **Each booking is written once.** A repeated "yes" doesn't create a second event or email.
- **Each write can be switched off** in the modal.

Setup:

1. Create a Google Cloud project and enable the Calendar API and Gmail API.
2. Configure the OAuth consent screen. External / Testing is fine; add yourself as a test user.
3. Create a **Desktop app** OAuth client.
4. Put the client ID and secret in `secrets/google.env` as `GOOGLE_CLIENT_ID=…` and `GOOGLE_CLIENT_SECRET=…`.

The redirect is the loopback URL `http://127.0.0.1:8765/api/connectors/google/callback`. Tokens are stored in the local SQLite database, and **Disconnect** revokes them.

Tests and evals use `FakeGoogle` and never reach Google. See `tests/test_connectors.py` and the eval scenario `google_calendar_busy_and_event`.

## How each requirement is met

- **Conversation and state.** `update_request` merges fields with provenance. Code computes `missing`, and the agent asks only for those. A correction changes one field and supersedes any open proposal. Phases come from a state machine with an allow-list (`workflow.py`).
- **Approval enforcement.** Proposals are built from the code's own hold and booking records. Approval comes from a deterministic parser and only for the proposal just shown. Side-effect tools are wrapped by `ApprovalGate.authorize`, and any change to provider, slot or price invalidates the approval.
- **Bounded execution.** `Limits` caps model calls, tool calls, wall-clock time and consecutive tool errors. Every exit produces a code-written message that also says nothing was changed.
- **Booking correctness.** The proposal is a write-ahead ledger with its idempotency key. A timeout goes to `get_booking_status` before any retry. Recovery on startup resolves anything still in flight. Success is shown only from verified executor results, and a claim guard catches model claims.
- **Untrusted output.** Reviews are scrubbed and flagged. Approvals and memory writes can't be granted by tool text: explicit memory needs a quote from the user's own messages.
- **Persistent memory.** SQLite stores explicit and inferred facts. Inferred facts are unconfirmed until the user confirms them. The agent can inspect, correct (supersede) and forget (tombstone plus history scrub).
- **Observability.** Per-run JSONL covers state transitions, context manifests, model calls (tokens, cost, latency), model-level and provider-level tool calls with sanitized results, approvals, executions and recovery.
- **Evaluation.** 35 scenarios, each checked against 5 global invariants plus scenario-specific outcome checks. The eval table is generated by the run.
- **Proactive follow-up.** A poller sees `provider_cancelled`. A code policy decides: ignore past bookings, notify only if you have another upcoming booking for that service, otherwise search for a replacement. The search uses your preferences and excludes the provider who cancelled, then needs fresh approval. Events are deduped.
- **Context management.** 54 seeded memories and a 300-message history under a fixed budget. Manifests log what was sent, and the tests replay the trace to prove that no forgotten or unconfirmed facts were sent.

## Model notes

**LiteLLM** (`ERRAND_LLM=litellm`): any provider or model LiteLLM supports. Set `ERRAND_MODEL` (e.g. `openai/gpt-4.1`) and that provider's key, or point `LITELLM_API_BASE`/`LITELLM_API_KEY` at a LiteLLM proxy. The adapter (`llm.LiteLLM`) converts the transcript to OpenAI tool-calling format and back. Cost comes from `litellm.completion_cost`. Everything else, including approvals, idempotency, memory and limits, is unchanged, because it's enforced in code, not by the model.


Set `ERRAND_RECORD=cassette.jsonl` to record a live session, then replay it offline with `--model replay:cassette.jsonl`.
